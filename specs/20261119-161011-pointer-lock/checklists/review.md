# Pre-tasks Review Checklist: Pointer Lock

**Purpose**: Check that the requirements are complete, clear and consistent before `/speckit-tasks`.
Focus areas: whether the spec agrees with the plan's decisions (silent suspension, release point,
bounding box, log reasons); scenarios the spec leaves open (camera jumps, re-shown windows, what counts
as the click that captures again); measurability; misbehaving and manual coverage. Depth: formal
pre-tasks review; audience: the owner.
**Created**: 2026-11-19
**Feature**: [spec.md](../spec.md) (with [plan.md](../plan.md), [research.md](../research.md),
[data-model.md](../data-model.md), [contracts/](../contracts/), [quickstart.md](../quickstart.md))

**Note**: This custom checklist is generated by the `/speckit-checklist` command based on feature context and requirements.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

Items marked "fixed" were corrected at the owner's request (2026-11-19, "fix the inaccuracies"). Items
marked "confirmed" carry a choice made while fixing that the owner confirmed on 2026-11-20 as
written; the spec, contracts and data model already state it.

## Spec vs Plan Decisions

- [x] CHK001 (fixed: FR-009 no longer lists zoom; a zoom keeps the constraint applying) Is FR-009
  consistent with US3 scenario 2 and research L6 about zoom? FR-009 lists "a zoom" among what
  suspends a constraint, while US3 scenario 2 says the constraint "keeps applying" during a zoom and
  research L6 says a zoom needs no suspension. [Conflict, Spec FR-009, Spec US3, Research L6]
- [x] CHK002 (fixed: FR-009 says pan, move and resize suspend it without telling the application)
  Does the spec say that a pan, a move or a resize suspends a constraint *without telling the
  application*? The application not being told is the core of research L6: without it, every pan
  ends a single-use lock. FR-009 says only "suspend". [Clarity, Spec FR-009, Research L6]
- [x] CHK003 (fixed: FR-007, US1 scenario 2 and the Edge Cases say "inside the lock's area as shown on
  the cursor's monitor", also when the application removes the lock) Is the condition for using the
  release point the same in the spec and the plan? FR-007 and US1 scenario 2 say "inside the window".
  Research L9 and the contract say "inside the window's effective area on the current viewer", which
  also excludes parts outside the lock area and parts not shown on that monitor. [Consistency, Spec
  FR-007, Research L9]
- [x] CHK004 (fixed: FR-012 and Misbehaving Clients name the 256-rectangle bound and the bounding
  rectangle) Is the bounding-box fallback for confinement areas of more than 256 rectangles
  (research L10, contract M6) reflected in the spec? FR-012 promises only "bounded time"; it does
  not say a hostile application's confinement may become looser. [Gap, Spec FR-012, Research L10]
- [x] CHK005 (fixed: FR-015 adds "a resize that left the cursor outside" and the lifetime; the
  plan's reason is now `Resize`) Does FR-015's list of reasons match the plan's? The plan adds
  "operation" (a resize leaving the pointer outside, research L13, data-model `ConstraintEnd`).
  [Consistency, Spec FR-015, Research L13]
- [x] CHK006 (fixed: Misbehaving Clients and FR-012 name the 32-subscription limit) Is the 32
  relative-pointer limit per application (research L11) acceptable without a mention in the spec's
  Misbehaving Clients? It changes what a (hostile) application receives. [Gap, Research L11]
- [x] CHK007 (fixed: the Assumption names both the release point and a shrinking confinement area)
  Is the Assumption "applications cannot move the cursor except through the release point of a lock"
  consistent with FR-014? FR-014 moves the cursor when a confinement area shrinks. [Consistency, Spec
  Assumptions, Spec FR-014]

## Scenario Coverage

- [x] CHK008 (confirmed by the owner 2026-11-20: the constraint stops, "cursor left"; a lasting one applies again
  when the cursor is over the area again; spec Edge Cases, research L6, contracts/input.md) Does the
  spec define what happens to a lock when the view jumps under a still pointer: Mod+0, or Mod+Tab
  bringing another window into view? The pointer then stops being over the window, so by FR-006 the
  lock stops ("pointer left"). Is that the intended result, or should the pointer follow the window,
  as after a pan? [Coverage, Gap, Spec FR-006, Contract input.md]
- [x] CHK009 (fixed: FR-008 and US1 scenario 4 say the window must receive the press; a press taken
  by a binding does not count) Is "a button press inside its window" (FR-008, capturing again after
  Mod+Escape) defined for a press taken by a binding (Mod + click, which pans)? Research L7 counts
  only presses delivered to the window; the spec does not say. [Ambiguity, Spec FR-008, Research L7]
- [x] CHK010 (confirmed by the owner 2026-11-20: hiding stops it, a single-use one ends; a lasting one applies again
  once the window is shown, focused and under the cursor; spec Edge Cases, data-model) Is the spec
  consistent about a window that is hidden and shown again? The Edge Cases say the constraint "ends".
  Research L12 reports a constraint again after `Mapped`, so a lasting one would apply again. Which is
  intended for a lasting constraint? [Conflict, Spec Edge Cases, Research L12]
- [x] CHK011 (confirmed by the owner 2026-11-20: a grabbing popup counts as a focus change, so a single-use one ends;
  the user must be able to use the menu; spec Edge Cases, FR-006) Is ending a *single-use* lock when
  the window's own popup grab opens intended? The Edge Cases say a constraint pauses while a popup
  takes the keyboard, but a single-use one cannot pause: it ends. [Clarity, Spec Edge Cases, Spec
  FR-006]
- [x] CHK012 (fixed: Edge Cases say RubickWay shows its own gesture cursor during a pan, move or
  resize, as `Shell::cursor` already does, and the hidden cursor returns afterwards) Does the spec
  define what the user sees during a pan or a move while the application has hidden the cursor
  (usual while locked)? Is there any cursor, RubickWay's or none? [Gap, Spec Edge Cases, Spec US3]
- [x] CHK013 (fixed: Edge Cases and FR-013 say a lock holds the cursor where it is, on its monitor)
  Does the spec cover a constraint whose window is visible on two monitors at once, for a lock (where
  does the lock point count) and not only for confinement (FR-013)? [Coverage, Spec FR-013]
- [x] CHK014 (confirmed by the owner 2026-11-20: the position in window coordinates counts, a popup of the same window
  on top does not stop it, so a tooltip under a locked cursor does not end the lock; FR-006, Edge
  Cases, research L5) Is the pointer over a popup of the constrained window (a tooltip, a
  non-grabbing popup) defined as "over its area" or not? The area is in the window's coordinates, and
  the popup may overlap it or sit outside it. [Ambiguity, Spec FR-006]
- [x] CHK015 (confirmed by the owner 2026-11-20: the cursor stays on screen; if still over the area, the constraint
  goes on and a lock holds at the window point now under it; otherwise it stops; Edge Cases, research
  L6) Is it stated what happens when the application maximizes or goes fullscreen while locked and
  the window grows or moves under the still pointer? The Edge Cases say "keeps applying to the window
  at its new size", but the lock point in window coordinates changes. [Clarity, Spec Edge Cases]
